## 2. Labels and descriptors
**Decision** (one per record and stage): `include`, `exclude` (one primary E-code + one-line paraphrased justification, D-089), `uncertain` (to full text; never dropped), `abstract_only` (full-text stage only).

**Required for `include` and `uncertain` at title/abstract (D-060 (6))**: `rq_tags`; `record_type` (`original / methodological / software / guideline / review_lead / other`, D-028 2d); `biomarker_class` (D-058); `dim_explainability`, `dim_uncertainty`, `dim_calibration` (`yes/no/unclear`); `validation_design` (`external / temporal / internal_only / none / not_applicable / unclear`, strongest stated). Optional for `exclude`. Stage-0 rule rows exempt.

**Meaning at title/abstract (D-029 as specified by D-060):**

| Descriptor | `yes` | `no` | `unclear` |
|---|---|---|---|
| `dim_explainability` | A **named** explanation/attribution method applied to the model's predictions (SHAP, LIME, permutation importance, PDP/ICE, counterfactuals, attention analysis, rule extraction, coefficients/odds ratios presented as the explanation) | Stated absence, or a fully described analysis that clearly contains none | "Interpretable/explainable/transparent" without a method; built-in importance without a named procedure; no abstract |
| `dim_uncertainty` | A **named** prediction-level uncertainty method (conformal sets/intervals, Bayesian predictive uncertainty, MC dropout, ensembles **used to quantify** uncertainty, abstention on an uncertainty score) | Stated absence, or fully described analysis with point predictions only | Ensemble/random forest without an uncertainty use; CIs of a **performance metric** only; "reliable/robust"; no abstract |
| `dim_calibration` | **Probability** calibration assessed or corrected, named (calibration plot/curve, slope/intercept, ECE/MCE, Hosmer–Lemeshow, Spiegelhalter, Platt/isotonic/temperature scaling) | Stated absence; or "calibration" only in the analytical-chemistry sense (stated in the justification) | Brier score alone; "well-calibrated" without method; no abstract |

These descriptors record **what the title/abstract states**, for triage only. They never count toward D-031/D-034 (D-035 G2). RQ5 component statuses are assessed at full text under D-035 §2 (unchanged; see §2a).

**`validation_design`:** `external` = different cohort/site/centre/country/public dataset; `temporal` = later patients, same source; `internal_only` = CV, bootstrap or random hold-out of the development cohort; `none` = apparent performance only; `not_applicable` = no predictive model evaluated; `unclear` = not stated, or "validation cohort" without origin, or no abstract.

**`publication_type`:** derived by the build from source metadata through the versioned D-028 mapping table (never hand-edited). arXiv records → `preprint` (D-028 2b). No URL- or DOI-prefix rules (D-028 2c). *Retracted Publication* sets the `retracted` flag only.

### 2a. RQ5 component evidence (D-031–D-038, unchanged from v0.1 §2a)
Five components, `yes` only for a qualifying procedure applied with a documented output (D-032; D-035 §2); `unclear` = assessed but unresolved; empty = not assessed. Statuses are **confirmed** only on a `full_text` row; a full-text RQ5 assessment records all five. The build derives `rq5_coverage_group` (`qualified` ≥ 4, `near_rq5` = 3, `below_threshold` 0–2) and `rq5_coverage_provisional` (D-034, D-036, D-037) from confirmed statuses; screeners never assign it. Researcher verification of `qualified`/`near_rq5` records: new `full_text` row with `screener=researcher` (D-035 G4). Reporting of four-`yes` subgroups per D-038. **`non_metabolic_rq5_candidate` at full text (D-075):** a component is *possible* when its full-text status is `yes` or `unclear`; every `full_text` row for the record, including verification and adjudication rows, carries the flag only when `yes` + `unclear` ≥ 3 among its five statuses, and otherwise omits it and explains why in the justification. Possible components are not confirmed components: `unclear` never counts as `yes`, and coverage groups are derived from confirmed statuses only. The title/abstract row keeps its flag unchanged.

## 5. Ambiguity handling, adjudication and audit trail
1. **When in doubt, `uncertain`.** Exclusion needs a positive reason found in the title/abstract.
2. **Every row records** `screener`, `date`, `justification` (≤ 1 sentence that paraphrases the decisive information; never a quotation from the abstract or other source text, because decision files are committed to the public repository; D-089) and `criteria_version` (the frozen version string). Enforced from the freeze: the validator then requires a version listed in `criteria_registry.json`, which is created only at the freeze and cross-checked against the freeze entry (D-085 B2–B4, commit `7f5b608`).
3. **Append-only:** decisions are never edited or deleted; a correction or adjudication is a new row (`screener=researcher` for adjudication; pilot adjudication rows use the distinct marker `screener=researcher:adjudication`, D-098 (d)), and the build uses the latest row per `paper_id` and `stage` while keeping all rows. The build rejects rows that blank a recorded component (D-036). Full-text and adjudication rows set `non_metabolic_rq5_candidate` by the D-075 rule (§2a).
4. **Adjudication queue** (`screening/adjudication_queue.csv`): every `uncertain`, every E12, every `needs_human=yes`, all possible-duplicate pairs. Built by `scripts/literature/pilot_agreement.py queue` (D-095) from the latest row per record and stage; every pair of `records/dedup_review.csv` is listed, a member without a decision with an empty `stage`; for the pilot it also lists every record on which the two screeners' decisions or primary codes differ.
5. **Criteria changes** after screening starts: question in `unresolved_questions.md`; accepted change logged in `DECISION_LOG.md` as a new criteria version; every record decided under the old wording with an affected code is re-screened.
6. **Provenance:** decisions refer to `paper_id` only; source records, raw exports and the manifest are never edited by screening. Inventory and reports are regenerated by the build, not by hand.
7. **Data protection:** no abstracts or raw records enter committed files (D-010).

## 7a. Assistant pilot procedure (integrated under D-100, Option A)
Governing decisions: D-025; D-063 and D-077 (sample); D-085 D1–D5 and D-087 (blinded sheet); D-088 and D-097 (run authorisation); D-089 (paraphrased justifications); D-093 (Stage-0 rows before the draw); D-094 (procedure clarified); D-096 (private sheet exchange); D-098 (pass-rule definitions); D-099 (run safety and ledger persistence); D-101 (no exposure of the assistant's decisions); D-102 (hash-first workflow; revision pending, step 5). **The pass criteria of D-025 are unchanged.** This section writes down how the approved steps of §7 are carried out; it adds no screening rule.

1. **Preconditions** (all recorded before step 2):
   - criteria v1.1 and protocol v0.2 are frozen, and `criteria_registry.json` names the frozen `criteria_version` (`criteria_v1.1+protocol_v0.2`, D-103);
   - the six D-035 record §6 conditions are recorded, one decision row each (D-092; D-097);
   - the Stage-0 rows have been written under a D-074 (f) authorisation (D-093);
   - the sample has been drawn under a D-077 (6) authorisation in the D-088/D-097 form (`screening/pilot_sample.csv` and its provenance sidecar);
   - the revision of D-102 is approved (step 5), and whatever it requires is in place; steps (3) and (4) of D-099 are implemented and tested.
2. **What the assistant sees.** Only the seven fields of the blinded sheet for each sampled record (`paper_id, title, abstract, abstract_status, year, venue, types`; D-085 D5; D-087), the same fields the researcher sees. The assistant does not use the stratum, retrieval themes, query IDs, verification status, `publication_type` or any other inventory field when it screens. It never sees the researcher's decisions, partial results or comments on individual records before its own decisions are fixed.
3. **Screening.**
   - Apply the frozen criteria v1.1 and protocol v0.2 exactly as written; do not change, reinterpret or tune them during the pilot. A difficulty with the criteria is written in `research/reviews/unresolved_questions.md`; it is not resolved during the pilot.
   - Write one `title_abstract` row per sampled record (screening-record format, criteria v1.1 §6; `screener=assistant`; the frozen `criteria_version`; required descriptors for `include` and `uncertain`, D-060 (6)).
   - Justifications: one line each, paraphrased; never a quotation (D-089).
   - Records without an abstract follow D-068 and are listed separately for the researcher's review.
   - Validate the file with `pubrecords.load_screening_decisions`.
4. **Blinding requirement (D-101).** The assistant's decisions are not exposed to the researcher (not shown, sent, summarised, committed or pushed) before the researcher's independent screening is complete and the researcher's decision file has been fixed.
5. **Hash-first workflow — [OPEN: revision of D-102 pending; clause (1) cannot be implemented as worded; R1 selected as the design, R2 as the fallback (D-109; design only)].** The pilot cannot start until the revision is approved. D-102 (3) (approved, conditional) requires custody by an **independent custodian**; no custodian is appointed. Under R1 the custodian would also receive the private sheet, which requires an extension of D-096 (not decided). Access control, key custody, commitment and disclosure are not implemented.
6. **The researcher's part.**
   - The researcher receives the blinded sheet privately; it is never committed (D-096). The researcher also receives the decision template (`pilot_agreement.py template`; paper IDs only).
   - The researcher personally records the 60 assessments in `pilot_decisions_researcher.csv` (`screener=researcher`); justifications are paraphrased (D-089).
   - After delivery, the file is validated and committed. The private sheet is then deleted from the working environment; it can be regenerated only under a new authorisation.
7. **Agreement and adjudication** (after verified disclosure only).
   - `pilot_agreement.py report` computes the §7 agreement measures and writes the metrics section of `pilot_report.md`, using the D-098 definitions. It refuses pilot files whose rows do not carry the expected screener.
   - `pilot_agreement.py queue` builds `screening/adjudication_queue.csv`: every `uncertain`, E12 and `needs_human=yes` row; every possible-duplicate pair; every disagreement.
   - The two screeners review the disagreements together. An agreed decision is a new `title_abstract` row for the same paper with `screener=researcher:adjudication`, in a separate adjudication file (§5 item 3; D-098 (b), (d)).
   - The pilot result is decided by the researcher; the computed evaluation does not approve it.
