## Q-098 — Crossref year field

**What the authoritative record uses** `[EVIDENCE: code]`: the PubMed year comes from `Journal/JournalIssue/PubDate` (Year, else MedlineDate). If that is missing, it comes from `ArticleDate/Year`, the electronic publication date (`pubrecords.parse_efetch_xml`). The PubMed connector route uses `publication_date.year`.

**Crossref date fields** (Crossref `/works` schema):
- `published-print`: the date of the print issue;
- `published-online`: the date of online publication;
- `issued`: the earliest of the two.

**Edge-case test** `[EVIDENCE: scratchpad probe, existing function pubrecords.crossref_year called with each candidate rule]`:

| Case | (a) print | (b) issued | (c) print → online | (c′) print → online → issued |
|---|---|---|---|---|
| Online-first: online 2020-12, print 2021-01 | 2021 | **2020** | 2021 | 2021 |
| Same year | 2021 | 2021 | 2021 | 2021 |
| Online only (no issue yet) | **none** | 2022 | 2022 | 2022 |
| `issued` only | none | 2019 | none | 2019 |
| No date fields | none | none | none | none |
| `date-parts: [[null]]` in a field used by the rule | **error** | **error** | **error** | **error** |
| `date-parts: [[]]` | **error** | none | **error** | **error** |
| Year as a string `"2021"` | 2021 | — | 2021 | 2021 |
| Implausible year (0) | none | none | none | none |

**Findings:**
1. **(b) `issued` mismatches by design** for online-first articles whose print issue falls in a later year. PubMed then shows the issue year, because PubDate refers to the issue. A mismatch is a conflict under D-064, so it gives `needs_review`. Rule (b) would therefore send exactly this common class to review, even though both sources are correct.
2. **(a) `published-print` alone** gives no year for online-only and ahead-of-print articles. These stay `partially_verified` (missing ≠ conflict).
3. **(c) print → online mirrors PubMed's own order** (PubDate → ArticleDate). It is the most consistent and reproducible choice, and it is deterministic: the first present field wins.
4. **Empty or null `date-parts` — correction (EXEC-SCAFFOLD-6).** Earlier this was called a defect. That was wrong: the committed robustness test `test_year_rule_rejects_malformed_date_parts` deliberately treats `[[]]` as **malformed**. The tool is fail-closed by design.
   - It becomes a problem only if a file is registered **before** the rule is set and the rule is set afterwards. The build would then refuse as a whole.
   - With the rule recorded **first**, the intake checks (`fetch_crossref.py`, `crossref_export_check.py`, `register_crossref_exports.py`, which refuses while the rule is unset) reject such a response at intake. The record simply stays `partially_verified`, which is the safe direction.
   - **No code change is needed beyond the rule constant.**

**Recommended rule** `[RECOMMENDATION]`: (c) `CROSSREF_YEAR_FIELDS = ("published-print", "published-online")`.
- `issued` is not used, to avoid the online-first false conflicts.
- A present field with an empty or null date stays malformed (fail-closed).
- Remaining real print-versus-online differences go through the existing review and override procedure (D-064 (8)).

**Implementation (prepared, not applied):** `research/reviews/2026-11-12_Q-098_proposed.patch`.
- It changes one constant in `pubrecords.py`.
- It pins the existing "no rule" tests to that state, so their coverage is kept.
- It adds one rule test.

`[EVIDENCE]` Applied in a scratch copy, the literature suite passed (379 tests OK). `git apply --check` against the real tree passed.

**Order constraint:** the patch changes `pubrecords.py` after `a0af2ad`. D-120 (a) records the tools "committed and tested at `a0af2ad`" for screening activation. The patch is therefore applied only **after** Stage 0 and the pilot draw have run under D-121 and D-122, at the authorised rebuild. It needs no code freeze exception before then.

**Until the researcher approves the rule, no record can become `verified` through Crossref.**

**Exact decision wording proposed** (implementation decision row, drafted in the decision sheet):
> "Q-098: Crossref year = first present of `published-print`, `published-online`; `issued` is not used; empty or null dates remain malformed (rejected at intake). I authorise applying `2026-11-12_Q-098_proposed.patch` (SHA-256 recorded at application) after the pilot draw, with the literature tests re-run, as part of the authorised rebuild."

## Q-099 — researcher-downloaded Crossref exports as "recorded retrieval"

**What D-064 requires** `[EVIDENCE: DECISION_LOG D-064 (10)]`: "PubMed ↔ Crossref or publisher record → `independent` only with recorded retrieval or checked-transcription provenance".
- The builder treats the route `crossref_api` (manifest route `crossref_works`) as recorded retrieval: it is in `RETRIEVAL_ROUTES` and needs no transcription check.
- The builder cannot tell a script download from a researcher download. Accepting a researcher download is therefore a governance reading, not a technical fact.

**What provenance establishes a retrieval** (all of these are needed):
1. **The exact request:** URL `https://api.crossref.org/works/<normalised DOI>`.
2. **The unchanged response body:** byte for byte, with its SHA-256 computed at download time and recomputed at registration.
3. **The response headers:** final status 200, and the server `Date` header (an independent time stamp).
4. **Who, when and how:** the researcher, the UTC time and the tool and version.
5. **The link to the inventory:** the paper ID, whose inventory DOI equals the requested DOI, and its listing in `records/verification_pilot.csv` (already enforced by the build).

**Proposed reproducible process** `[RECOMMENDATION]`:
1. The researcher runs, for each record to be cited:

   ```bash
   curl -sS -D CR_<n>.headers.txt -o CR_<n>.json "https://api.crossref.org/works/<doi>"
   ```

   They name the files `CRX_<YYYY-MM-DD>_<nnn>.json` and `.headers.txt`, a prefix distinct from the fetcher's `CR_` files. They save both files in `research/literature/raw_exports/`, which is Git-ignored and backed up off-device under D-010, and fill `provenance.csv` (columns: `file, headers_file, doi, paper_id, url, retrieved_at_utc, tool, exported_by, sha256`).
2. The assistant runs the read-only checker `scripts/literature/crossref_export_check.py <dir> --inventory research/literature/paper_inventory.json`. It refuses any of:
   - a hash mismatch;
   - a DOI mismatch;
   - a wrong URL;
   - a non-200 status or a missing `Date` header;
   - a missing or non-UTC time stamp;
   - a duplicate;
   - a malformed body;
   - an inventory DOI mismatch.

   It writes nothing. It has 8 synthetic tests.
3. Only after the researcher approves Q-099, Q-098 and the export list, `scripts/literature/register_crossref_exports.py --write` registers accepted files. It refuses while the year rule is unset, without an authorisation reference, outside `raw_exports/`, on any failed check, and for a file already registered (3 tests). It uses the existing `pubrecords.register_raw` under `VERIFY-CR-<paper_id>`, with `endpoint_or_tool` "researcher export: <tool>, <UTC>" and the header file named in `notes`. Then the authorised rebuild runs, followed by a new fixed-inventory entry.
4. The verification report lists these records as researcher-retrieved, so a reader can tell them apart from script retrievals.

**Exact decision wording proposed:**
> "Q-099: a Crossref /works response downloaded by the researcher counts as recorded retrieval under D-064 (10) when it passes `crossref_export_check.py` and is registered with its researcher-export provenance; D-064 itself is unchanged."

**Alternative:** require script retrieval only. This needs `api.crossref.org` to be allowed for the container, which is a network setting the researcher controls. It would make the provenance uniform, but it is not available now.

## Q-100 — the internal reference for Q3 (temporal transfer)

**The difference:**
- The frozen model is **calibrated**: Platt calibration is fitted on D-cal, and every temporal-validation metric uses calibrated probabilities.
- The v0.1 internal estimate uses **uncalibrated** out-of-fold predictions.
- Q3 measures the change from internal to temporal validation.
- With an uncalibrated reference, the change in a calibration metric (ICI, slope, intercept, Brier) contains two effects: (i) what calibration did, and (ii) what the change of period did. Q3 is meant to measure only (ii).
- AUROC is unaffected, because Platt with a positive slope is order-preserving.

**Synthetic illustration** `[EVIDENCE: simulated scores, no model fitted; scratchpad script q100_illustration.py]`:
- Setup: overconfident raw scores; Platt calibration fitted on a separate calibration set.
- In the validation period, the scores are offset relative to the true risk (a measurement shift).

| Shift in validation | Internal ICI, raw | Internal ICI, calibrated | Temporal ICI | Q3 change vs raw reference | Q3 change vs calibrated reference |
|---|---|---|---|---|---|
| none | 0.108 | 0.038 | 0.026 | −0.082 | −0.012 |
| 0.3 | 0.104 | 0.006 | 0.055 | **−0.049** (looks better) | **+0.049** (worse) |
| 0.6 | 0.114 | 0.020 | 0.120 | +0.006 (looks unchanged) | +0.100 |

With the raw reference, a genuine loss of calibration in the new period can appear as an improvement or as no change. AUROC was identical between the raw and calibrated estimates in every case (0.804, 0.796, 0.778).

**Options:**
- **(A) Calibrated internal reference** `[RECOMMENDATION]`: out-of-fold predictions on D-train passed through the D-cal calibrator.
  - Like for like with the frozen model.
  - D-cal is disjoint from D-train, so the reference is not fitted to itself.
  - Small caveat: the out-of-fold predictions come from fold models, not from the single refitted model. This is stated in the paper.
- **(B) Uncalibrated reference (v0.1 wording).** It reproduces the confounding shown above for calibration metrics. It is acceptable only for AUROC and AUPRC.
- **(C) Both,** with (A) declared primary and (B) reported. The harness already records both. This is the same as (A) for any conclusion.

**Implications:**
- (A)/(C) need one sentence in FA-11, at the freeze.
- They change no data, model or other analysis.
- Q2 is unaffected: it compares calibrated models with each other.

**Exact decision wording proposed:**
> "Q-100: the Q3 internal reference is the calibrated out-of-fold estimate (`internal_calibrated_summary`); the uncalibrated estimate is reported alongside."

## Q-054 — AUROC non-inferiority margin (needed before D-019)

**Facts:**
- v0.1 makes AUROC a non-inferiority comparison in Q2 but gives no margin.
- No `verified` record justifies a margin or a net-benefit threshold range: none is verified.
- A margin chosen after the results are seen would be invalid (CLAUDE.md rules 4 and 16).

**What a non-inferiority claim needs:**
- a margin δ fixed before the freeze, with a stated justification (a clinical or literature basis);
- a decision rule: the lower 95% bound of ΔAUROC (framework − baseline) > −δ, implemented as `compare.non_inferior`;
- a multiplicity statement (Holm across the six baselines if each is a claim).

**Options:**
- **(a) Formal non-inferiority with margin δ:**
  - permits the statement "not worse by more than δ";
  - the value is the researcher's, with its justification;
  - risk: an unsupported δ is a predictable reviewer objection, and without a verified source it would be arbitrary.
- **(b) No formal non-inferiority claim** `[RECOMMENDATION]`:
  - ΔAUROC is reported with its paired-bootstrap 95% CI;
  - the paper says "the difference was x (95% CI y to z)", without a non-inferiority verdict.

  **Consequence:** the research question's phrase "with discrimination comparable to established baseline methods" (Q-016, provisional) must then be read descriptively, or reworded. Proposed reading: "comparable" is assessed by reporting the ΔAUROC CI, not by a test. This wording is the researcher's (Q-016, D-016).
- **M10 (net benefit):** without a justified threshold range, it is either descriptive only (0.05–0.95, no conclusion) or dropped.

**Exact decision wording proposed:**
> "Q-054: option (b) — no formal non-inferiority claim; ΔAUROC reported with its paired-bootstrap 95% CI; M10 [descriptive only / dropped]; the research question's 'comparable discrimination' is read descriptively."
